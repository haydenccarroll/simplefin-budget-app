# budget-api

REST API backing the SimpleFIN Budget App mobile app. Implements a zero-based budgeting model: every dollar
of planned income is assigned to a category line item until nothing is left unbudgeted, and every
real-world transaction is logged against a line item to track actual vs. planned spend.

The OpenAPI spec can be generated by running `make docs`.

## Domain model

- **Budget month** — one per calendar month per user (`2026-09`). Created on first access, optionally
  copying groups/line items/planned amounts forward from the prior month.
- **Income items** — planned (and actual) income for the month.
- **Category groups** — sections like "Giving", "Savings", "Housing" that contain line items.
- **Line items** — a planned amount to budget for something (e.g. "Groceries: $600"). Spent amount is
  derived from transactions.
- **Transactions** — real spending, optionally assigned to a line item.

## Endpoints

- `GET  /v1/budget-months` — list months that exist for the user
- `GET  /v1/budget-month/{month}` — full nested view: income, groups, line items, spent/remaining, totals
- `POST /v1/budget-month/{month}` — create the month, optionally `?copy_from=previous`
- `POST /v1/budget-month/{month}/income-item`
- `PATCH /v1/income-item/{id}`
- `DELETE /v1/income-item/{id}`
- `POST /v1/budget-month/{month}/category-group`
- `PATCH /v1/category-group/{id}`
- `DELETE /v1/category-group/{id}`
- `POST /v1/category-group/{id}/line-item`
- `PATCH /v1/line-item/{id}`
- `DELETE /v1/line-item/{id}`
- `GET  /v1/budget-month/{month}/transactions`
- `POST /v1/budget-month/{month}/transaction`
- `PATCH /v1/transaction/{id}`
- `DELETE /v1/transaction/{id}`

## Budgets, members and sharing

A budget is owned by one user and shared with any number of members (roommates, a spouse), who join with the
budget's friend code. Every user is in at most one budget, and all data (months, income, categories, expenses,
the bank link) belongs to a budget: a request only ever sees its caller's. Someone with no budget gets `403` with
`{"code": "no_budget"}` from every data endpoint until they create or join one.

- Only the owner connects a bank: they send a SimpleFIN setup token to `PUT /v1/simplefin/connection`, the API claims it
  at once and keeps just the access URL it gets back (the token works once, so it isn't stored). Everyone in the budget
  syncs through that connection.
- The app asks for a sync (`POST /v1/budget-month/{month}/sync`) every time it loads or refreshes. A budget that was
  successfully synced in the last 15 minutes isn't synced again: the call returns `200` at once with `throttled: true`.
- A new budget has no friend code, so nobody can join it. The owner generates one (8 letters and digits, shown as
  `ABCD-EFGH`; generating again replaces it and the old one stops working) and can delete it to switch joining off
  again. Any member can see the code; only the owner changes it. Removing a member does not change it.
- Expenses and income items accept an optional `client_id` (a UUID). The app sets it on entries made offline and sends
  them later; sending the same `client_id` for the same month again returns the saved entry (`200`) instead of adding a
  duplicate (`409` if that entry was since deleted).
- A removed or departed member keeps their account and goes back to create-or-join; what they entered stays.
- The owner can't leave; deleting the budget is how it ends.

Endpoints (all authenticated):

- `GET    /v1/budget` — the caller's budget: friend code (`null` when joining is off), members (usernames and names), `is_owner`
- `POST   /v1/budget` — create a budget with the caller as owner (`409` if already in one)
- `POST   /v1/budget/join` — `{"friend_code": "ABCD-EFGH"}` (`404` unknown code, `409` already in one)
- `POST   /v1/budget/friend-code` — owner only: generate a friend code, or replace the current one
- `DELETE /v1/budget/friend-code` — owner only: delete the friend code so nobody can join
- `DELETE /v1/budget/members/{user_id}` — owner removes anyone else; a member may remove only themselves
- `GET    /v1/simplefin/connection` — the budget's linked bank accounts (`connection` is `null` when there is none)
- `PUT    /v1/simplefin/connection` — owner only: `{"setup_token": "..."}` connects (or replaces) the bank
  (`422` if SimpleFIN rejects the token, `502` if the bridge can't be reached)
- `DELETE /v1/simplefin/connection` — owner only: disconnect the bank; already-imported transactions stay
- `GET    /v1/budget/export` — every month with records as one CSV: `summary`, `income`, `category` and `expense`
  rows (see `internal/handlers/budgetadmin/export.go`). Text cells that look like formulas are neutralized.
- `DELETE /v1/budget/data` — owner only: permanently deletes the whole budget: every month (income, categories,
  expenses), the bank link, every membership and the friend code. Everyone who was in it (the owner too) is left with no
  budget and can create or join another; accounts are untouched.

Wrong friend codes are rate limited: a user who submits 10 unknown codes in an hour gets `429` until the hour is up.

## Accounts and sessions

The API is the only backend: it signs people up, signs them in, and decides what they may touch. Passwords are
argon2id hashes; a session is a random 256-bit token whose SHA-256 is stored, so a copy of the database can't be
used to sign in. Sessions last `SESSION_LIFETIME` (30 days).

A request is authenticated by either credential, checked by `internal/auth/middleware.go`:

- **`Authorization: Bearer <token>`** for native apps. They ask for the token by sending `X-Session-Mode: token` on
  login or registration, and it comes back in the body as `token`.
- **The `budget_session` cookie** for browsers. It is `HttpOnly` and `SameSite=Lax` (and `Secure` when
  `COOKIE_SECURE=true`), so scripts can't read it and other sites can't send it. As a second wall against CSRF, a
  state-changing request that carries the cookie must have an `Origin` that is the API's own or in
  `CORS_ALLOWED_ORIGINS`, and any state-changing request from a disallowed origin is refused. CORS answers only for
  those listed origins, with credentials (never `*`).

Nothing a client sends about *who* it is is believed except the token: a request with a made-up `X-User-ID` is just
anonymous. Which budget a user may touch, and whether they own it, is decided from the `budget_members` table on every
request, and everything is scoped to that budget in SQL (see `internal/handlers/budget/budget.sql`).

Endpoints (`/v1/auth/...`, public unless noted):

- `POST /v1/auth/register` — `{username, password, first_name, last_name, timezone}` creates the account and signs it in
  (`409` if the username is taken). Usernames are 3 to 30 letters, digits, `.`, `-` or `_`, case-insensitive; passwords are
  8 to 128 characters.
- `POST /v1/auth/login` — `{username, password}` (`401` wrong username or password, `429` too many wrong ones)
- `POST /v1/auth/logout` — ends the current session
- `GET  /v1/auth/me` — signed in: the account (`id, username, first_name, last_name, timezone`)
- `PATCH /v1/auth/me` — signed in: change `first_name`, `last_name`, `timezone` and/or `username`. Changing the username
  needs `current_password`.
- `POST /v1/auth/change-password` — signed in: `{current_password, new_password}`; every other session is signed out

There is no email, so there is no way to recover a forgotten password.

Wrong passwords are limited per username and per address, and sign-ups per address (`internal/ratelimit`; counts live in the
process). Set `TRUST_PROXY_HEADERS=true` behind a reverse proxy so "address" means the client's, not the proxy's.

Other notes:

- Request logs hold the method, path and status only, never bodies or query strings.
- Request bodies are capped at 1 MiB and the server has read/write timeouts.
- `GET /metrics` is not on the public port; set `METRICS_ADDR` (e.g. `:9090`) to serve it separately.
- Registering with a taken username says so (`409`), so usernames can be probed; that is the usual trade.

## Configuration

Environment variables (see `internal/config/config.go`; `docker-compose.yml` sets them for you):

| Variable | Meaning |
| --- | --- |
| `DATABASE_PATH` | the SQLite database file, shared by the API and the worker (default `budget.db`) |
| `SERVE_PORT` | port to listen on (default 8080) |
| `CORS_ALLOWED_ORIGINS` | web origins allowed from a browser, comma separated |
| `COOKIE_SECURE` | mark the session cookie `Secure` (HTTPS) |
| `SESSION_LIFETIME` | how long a sign-in lasts (default 720h) |
| `TRUST_PROXY_HEADERS` | rate limit by the last `X-Forwarded-For` address |
| `CATEGORIZATION_ENABLED` | queue uncategorized expenses for the worker (only useful when the worker runs) |
| `RUN_WORKER` | run the categorization worker inside the API process (turns on categorization) |
| `LITESTREAM_ACCOUNT_NAME`, `LITESTREAM_CONTAINER`, `LITESTREAM_AZURE_ACCOUNT_KEY` | Docker image only: restore the database from Azure Blob Storage on start and replicate it there (`docker/litestream.yml`) |
| `JOB_RETRY_DELAY` | how long a failed categorization job waits before it is retried (worker, default 1m) |
| `LLM_URL`, `LLM_MODEL` | the Ollama server and model (worker) |
| `SIMPLEFIN_CLAIM_HOSTS` | bridge hosts SimpleFIN tokens may be claimed from |
| `METRICS_ADDR` | serve Prometheus metrics on this address |

## Database

Everything lives in one SQLite file (`DATABASE_PATH`). The API and the worker open the same file; it runs in WAL mode
with a busy timeout, so they take turns writing instead of failing. Both apply any pending migrations when they start,
so there is no separate migration step.

Migrations are `internal/database/migrations/NNN_name.sql`, embedded in the binary and recorded in
`schema_migrations`. There is a single one, `001_init`, holding the whole schema. Nothing has been deployed yet, so it
is edited in place rather than added to; once there is a deployed database, changes go in new numbered migrations.

Queries are written in the `.sql` files next to their handlers and compiled with [sqlc](https://sqlc.dev)
(`make sqlc-generate`, output in `internal/queries`).

To back up a running database, use SQLite's online backup rather than copying the file mid-write:
`sqlite3 budget.db ".backup backup.db"`.

## Background jobs

Automatic categorization runs in the `worker` subcommand. The API queues work as rows in the `jobs` table
(`internal/queue`); the worker polls for due jobs, claims one by locking it for a lease, and deletes it when done. A
failed job waits `JOB_RETRY_DELAY` and is retried; after 8 failures it is parked (`dead_at` is set, with `last_error`)
for inspection. If the worker dies mid-job, the lease runs out and the job runs again, so jobs must be idempotent.
